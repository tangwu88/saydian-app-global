# U19 血压与查找设备桥接闭环（2026-09-28）

## 范围和基线

- 基线 `41fe3e5677c69821c9a544a9437bdb6ab67317e2`，工作区及远端由主任务核对，保留其他代理修改。本次延续用户明确授权的修复，仅修改 EB1 协议、U19 桥接、健康通知路由及对应测试。
- 原问题：能力未开放血压/查找；固定响应数量不能正确结束不足 50 条的血压历史；操作入队时未固定会话，换表后可能执行旧操作；单次测量缺少前后历史与时钟证明。属于 P1 核心链路问题。
- 预期：只有新会话实际回包能生效；只读能力验证不启动测量；ACK 不冒充测量结果；无法证明的历史不上传，不固定减 8 小时。未修改算法、云端协议、用户原数据或手表设置。

## 协议与实现

1. 核对用户提供的备注版 EB1 DOCX：`0x14` 为时间戳 LE4＋方向＋数量（最大 50）；不足数量以全 `FF` 时间戳结束。收集器按数量或哨兵结束；校验有效值，不把哨兵当零记录。
2. `0x15/0x2D` 按头包声明数量收集，支持无数据结束、重复相同包忽略、缺包/冲突包拒绝。4 包血氧单值结构可解码；5 包 min/max 结构继续拒绝。HR/O2 尚无本轮完整真机证明，能力保持隐藏。
3. U19 每个排队操作在调用时捕获会话和设备，执行前、返回后、实际写入前均复核；旧超时不得断开新会话。格式错误使当前连接退役，避免剩余历史污染后续命令。
4. 验证后的 EB1 通道按协议配置开放查找；`0x50 55 AA` 必须得到有效应答才完成。收到不支持应答立即撤销能力并通知页面，后续调用不再次发送。物理振动仍需用户/真机确认。
5. 血压能力通过只读历史结构确认（有效无数据哨兵也可确认），不靠发起测量探测。开始前保存已有记录签名；已有历史不妨碍开始。发送 `0x32` 并收到 ACK 后只表示开始已确认。
6. 只有 `0x73 type 2` 或 `0x33` 通知才为当前血压测量排队回读。必须发现快照中不存在、且时间戳在开始/结束窗口中唯一匹配 UTC 或本地墙钟解释的新样本，才发 `healthRecord`，包含 `origin: appMeasurement` 和 UTC `measurementStartedAt` 证明。重复通知、重复历史包只发一个结果。无法确认时继续等待，不生成伪进度或成功。
7. 两种时钟解释若产生同一时刻，可确认该次结果，但不认定历史编码；否则只采用唯一匹配解释。编码仅在当前连接保存；更早记录可能在用户调准时钟之前，继续不上传。已确认手动样本在后续历史回读保留相同不可变内容和来源。
8. 新的用户确认开始替换旧等待上下文，不发送协议不存在的停止指令。断线/换表清除上下文；返回旧结果或旧开始证明不能结束新测量。
9. 真实健康变化通知仅接受 `0x73 type 1/2/3/4/6` 和 `0x33`；携带 `source: watchNotification` 及设备 ID。路由补 `urion:` 前缀（已带前缀不重复），避免控制器拒绝当前设备通知。
10. `kDebugMode` 增加能力结构确认、开始 ACK、结束通知、唯一结果确认/编码类别及查找 ACK 标记。不记录健康值、原始时间戳、设备标识或凭据。原日汇总与时间语言选择逻辑保留。
